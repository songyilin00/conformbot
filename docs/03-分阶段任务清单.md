# 分阶段任务清单

> 本文档将项目拆为 **Phase 0–4** 的开发任务，每个 Task 含：目标、具体指令、参考文档、验收标准。
> 依据 §10.2 分阶段对接策略、§4 演进路径、§9 产品形态；具体指令为【建议/待确认】推演。

## 阶段总览

| Phase | 主题 | 核心产出 | 对应项目文档 |
| :--- | :--- | :--- | :--- |
| **Phase 0** | 地基 | 数据模型 + SBOM 导入（CSV/Excel 手动）+ 存储 | `04` §一–§三 |
| **Phase 1** | 判断引擎 | CVE→合规多层过滤、状态标签、变更性质识别 | `04` §四–§七 |
| **Phase 2** | 主动推送与看板 | BOM 过滤推送、健康度色标、多框架独立告警 | `04` §八 ｜ `06` |
| **Phase 3** | 静默修复 + 语义级变更分析 | 接静默修复方法 + 本地 LLM | `02` §四/§八 ｜ `04` §六 |
| **Phase 4** | 对接与门禁 | MCP(PLM) / hawkBit(OTA) / 发布前门禁 / 回写 ECN | `02` §六/§七 ｜ `05` §六 |

## 前置原则（每个 Task 都适用）

1. 遵守「身份是 Bot」——产出必须服务于「主动 / 自主 / 在场」（见 `01` §二）。
2. 遵守「判断不越位」——GEC-1 终裁归制造商（见 `04` §五）。
3. 每条判断结论须**可回溯到依据**（条款版本 + 数据点 + 命中规则）。
4. 参考 `07-通用开发规范.md`，禁止在生产路径出现未处理异常。

## Phase 0：地基

### Task 0.1：数据模型与存储

**目标**：按 `04` §一 落地 ER 实体的数据模型与持久化。

**具体指令**：
1. 定义实体：Product / Firmware / SBOM / Component / CVE / CVE_Assessment / Change_Assessment / Vuln_Ticket / OTA_Record / Audit_Record。
2. 建立表结构与索引（组件版本精确到补丁级）。
3. 实现审计记录表与哈希链字段（`04` §九）。

**参考**：`04-数据模型与判断逻辑.md` §一/§九/§十。

**验收**：实体表可创建；可插入一条审计记录并校验哈希链。

### Task 0.2：SBOM 导入

**目标**：支持 CSV/Excel 手动导入安全相关 BOM 子集（MVP）。

**具体指令**：
1. 定义「安全 BOM 子集」导入模板（`04` §三）。
2. 解析并落库；对组件名/版本做规范化。
3. 校验：版本精确到补丁级；缺失字段报错。

**参考**：`04` §三 ｜ `02` §二。

**验收**：可导入一份样例 SBOM，组件数正确、版本规范化正确。

### Task 0.3：CycloneDX / SPDX 解析

**目标**：支持标准 SBOM 格式解析。

**具体指令**：
1. 接入 CycloneDX / SPDX 官方解析库。
2. 映射到 Component 实体；保留 purl、VEX 信息。
3. 只保留安全相关子集。

**参考**：`02` §二。

**验收**：可解析一份样例 CycloneDX 与 SPDX 文件。

## Phase 1：判断引擎

### Task 1.1：CVE 多层过滤

**目标**：实现 `04` §四 的四层过滤与状态标签。

**具体指令**：
1. 组件 + 版本精确匹配。
2. 公开利用证据判定（PoC / CISA KEV / 在野证据）。
3. 保护范围判定（安全资产 / 网络资产）。
4. CVSS/EPSS 仅作排序。
5. 输出四态标签：必须修复 / 建议修复 / 仅监控 / 不适用。

**参考**：`04` §四/§五 ｜ `02` §三。

**验收**：对样例 CVE 集输出正确状态标签（含不适用排除）。

### Task 1.2：变更评估引擎

**目标**：实现「变更性质识别 → 结论分级」。

**具体指令**：
1. 识别是否触及加密算法/认证协议/OTA 签名/安全启动链。
2. 未触及 → 标记「内部评估完成，证据假设未变」并归档。
3. 触及 → 标记「需变更评估」；按 NB 证书提示备案/差异测试。
4. 结论分级：reassess / recertify。

**参考**：`04` §七。

**验收**：对样例变更（如 mbedtls 2.28.1→2.28.4）输出正确结论与 NB 提示。

## Phase 2：主动推送与看板

### Task 2.1：多框架独立告警

**目标**：实现「一 CVE 对每框架一条独立告警，不合并」。

**具体指令**：
1. 数据模型：告警带 framework + 依据 + 严重级（`04` §八）。
2. 禁止跨框架自动合并/抑制。
3. 提供按框架筛选、按严重级排序。

**参考**：`04` §八。

**验收**：同一 CVE 触发 EN 18031 与 CRA 时产生两条独立告警。

### Task 2.2：主动推送与信号分级

**目标**：实现「日常静默，仅整改级才推送」。

**具体指令**：
1. 按 BOM 过滤，只推送影响该产品的 CVE 与标准变更。
2. 信号分级：形如「本周新增 2 个监控项，0 个需立即处理」。
3. 事件驱动推送渠道（见 `05` §五）。

**参考**：`01` §二/§十 ｜ `06` §八。

**验收**：无整改级时静默；有整改级时主动推送且带依据。

### Task 2.3：合规状态看板

**目标**：实现健康度色标看板。

**具体指令**：绿/黄/红三态（`04` §十）；各模块卡片/表格。

**参考**：`06` §三。

**验收**：看板能准确反映当前合规状态。

## Phase 3：静默修复 + 语义级变更分析

### Task 3.1：静默修复检测

**目标**：覆盖 SCA 盲区，标记「静默安全修复」。

**具体指令**：集成 Fixseeker / SPDAgent / Lacuna 之一或组合（`02` §四）。

**参考**：`04` §六 ｜ `02` §四。

**验收**：对含未披露修复的组件更新，能标记为「静默安全修复」。

### Task 3.2：本地 LLM 语义级变更影响分析

**目标**：用本地 LLM 给出「带依据的初判」。

**具体指令**：
1. 本地部署 Qwen 27B 级模型，文档不外传。
2. 解析 CVE 描述、变更日志、条款决策树。
3. 输出如「此变更触及 SCM-1 通信加密要求，建议启动差异评估」，附出处。

**参考**：`01` §十一 ｜ `02` §八。

**验收**：给定样例变更能输出带依据的语义级初判，且不越位终裁。

## Phase 4：对接与门禁

### Task 4.1：MCP（PLM）对接

**目标**：接入 PLM 的 MCP Server。

**指令**：以 MCP Client 消费 PLM 的安全 BOM 子集。**参考**：`02` §六 ｜ `05` §六。

**验收**：能从 PLM 拉取成分基线。

### Task 4.2：OTA Management API 对接

**目标**：接入 hawkBit REST API。

**指令**：读取变更事件；**发布前设合规门禁**。**参考**：`02` §七 ｜ `05` §六。

**验收**：发布前可按判断结论放行/拦截。

### Task 4.3：结果回写与双向集成

**目标**：判断结果回写 ECN / OTA。

**指令**：webhook/API 双向集成；标准接口覆盖 80%，其余按项目收费。**参考**：`05` §六。

**验收**：判断结果能回写目标系统并留审计。
