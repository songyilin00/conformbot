## 项目名称

ConformBot（合规值守官）。

## 一句话定位

**ConformBot 不是扫描器，也不是认证机构，而是一个「合规判断引擎」——一个持续在岗的值守代理。**

它消费厂商已有的 SBOM（来自 SCA 工具或 CI/CD），在 EN 18031 / CRA 等条款下，持续判断「每一次组件变更、每一次 OTA、每一个新披露的 CVE，是否触碰了合规规则、是否需要重新评估」，并把每一次判断留下可审计的证据。

## 核心承诺

> 厂商要的不是「又一个漏洞列表」，而是「这次变更到底要不要走重评估流程」的即时、带依据的答案。
> **形态可以极简，身份必须是 Bot**（主动 / 自主 / 在场）；价值在「持续在场」，不在结果担保。

## 设计原则（贯穿全项目）

1. **身份是 Bot，不是工具** —— 主动、自主、在场三性不可漂移；最需对抗的内部风险是「工程上越做越像工具」。
2. **判断，而非平台** —— 只做「变更 → 合规结论」的判断；不碰固件、不建平台、不替代 PLM/OTA。
3. **多框架独立告警** —— 同一 CVE 触碰多个框架即产生多条独立告警，不自动合并或抑制。
4. **判断不越位** —— GEC-1 的最终「可利用性」由制造商结合产品语境确认；引擎只做初判 + 证据结构化。
5. **不承诺赔付、不承诺包过** —— 价值在「持续在场」，不在结果担保。
6. **信号分级严格** —— 日常静默，仅在达到「整改级」时主动推送，不做实时告警轰炸。
7. **低摩擦接入** —— 第一版手动导入即卖点：无需 IT 协作、无需开 API 权限、上传一个文件即可开始。
8. **法规条款版本可溯** —— 每条判断结论必须绑定其所依据的标准/条款版本与时间点。

## 目标端与角色

| 端 | 说明 |
| :--- | :--- |
| 判断引擎（核心服务） | 消费 SBOM 与变更事件，在框架条款下产出结构化合规结论 |
| 数据接入层 | SBOM 导入、变更事件录入、外部 CVE/标准数据拉取 |
| 仪表盘（审计控制台） | 用户可见的合规状态、告警、工单与审计入口；**是副入口，不是主入口** |
| 外部数据源 | SBOM / CVE 库（NVD/EUVD/GitHub Advisories/CISA KEV/EPSS）/ 标准动态 |

> ⚠️ 不要把「Bot」理解成「聊天机器人」——B2B 合规买方要的是证据链与审计轨迹，不是对话框。
